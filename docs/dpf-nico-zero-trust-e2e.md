# OpenShift DPF Zero Trust with NICo

This repository deploys NICo. The OpenShift DPF automation owns the DPF platform and HostedCluster lifecycle. NICo owns the DPU inventory and the DPF resources generated from its site configuration; DPF controllers provision the DPU and reconcile those resources. Do not run the standalone DPF workload-manifest path when NICo owns the deployment.

**End-to-end hold for preinstalled OpenShift workers:** the lab reached a running NICo DPU agent and DPF services, but NICo then entered its generic `HostInitializing` path for the x86 worker, placed HTTP/Scout first in the host boot order, and waited for Scout measurements. Its later initial-discovery path can request a disk cleanup. Until NICo supports adopting an externally provisioned OpenShift worker, or the host-ownership sequence is changed and validated, do not run this procedure through host onboarding on an installed worker. The remaining steps describe the intended DPF/NICo handoff and its prerequisites; they are not a claim of a passed full deployment.

## Deployment sequence

Use the NICo integration in [openshift-dpf PR #510](https://github.com/rh-ecosystem-edge/openshift-dpf/pull/510). It preserves the standalone DPF flow by default and adds an explicit NICo handoff:

1. In the DPF automation's protected `.env`, set `DPF_DEPLOYMENT_MODE=zero-trust`, `NICO_ENABLED=true`, and `NICO_DPU_DEPLOYMENT_NAME` to the deployment name used by the NICo site configuration.
2. Run the DPF platform stage (`make all-zt`). In NICo mode it installs DPF and the HostedCluster prerequisites, then stops before creating the HostedCluster.
3. Make the configured DPUService Helm charts available from the site chart repository, then deploy NICo with this repository's `make deploy-all-site` target and the appropriate per-site values. The NICo site configuration must keep `[dpf].enabled = true` and define the matching DPU deployment, BFB, services, and images. On sites without a data-plane VIP, use `make deploy-dpf-endpoints` from [NCP PR #32](https://github.com/rh-ecosystem-edge/ncp-dsx-nico-deploy/pull/32) after the site deployment so DPU agents can reach the NICo API and PXE routes. This target is not present in the base of this documentation PR.
4. After NICo creates the configured `DPUDeployment`, continue with `make deploy-hosted-cluster` in the DPF automation. Once the HostedCluster API is ready, run `make deploy-dpu-services` to apply the hosted-cluster DPF authorization.
5. DPF controllers provision the DPU and reconcile NICo's DPU services. Verify the DPU and HostedCluster worker conditions, the current DPU's service interfaces, and NICo's managed-host state before treating onboarding as complete.

The exact DPF targets and required settings are owned by the [DPF automation](https://github.com/rh-ecosystem-edge/openshift-dpf/pull/510). Keep `DPF_DEPLOYMENT_MODE`, `NICO_ENABLED`, and `NICO_DPU_DEPLOYMENT_NAME` in that repo's environment; they are not NCP Helm values or `deploy.env` settings.

## NICo site configuration

Use the existing NCP targets rather than a wrapper that calls a second repository's Makefile. Put deployment-specific NICo DPF settings in the per-site Core site configuration (`helm/values/nico-core-<SITE>.yaml`), including the same DPU deployment name supplied to DPF. Keep credentials in the DPF automation's protected environment or a cluster Secret; do not commit BMC passwords, pull secrets, or kubeconfigs. The checked-in `deploy.env.example` is for safe NCP site-selection values, not secrets or DPF orchestration.

Keep the `nico-api` control loop on a management node that will remain powered during DPU-host provisioning. NICo's DPF reboot handler powers the host off, then later sends the power-on command; colocating the API pod with that host strands the second step. The upstream `nico-api` chart accepts `nodeSelector`, so set `nico-api.nodeSelector` in the site values to a suitable management-node label and verify the pod placement before onboarding. The lab uses its management SNO hostname as the selector; do not copy that hostname to another site.

Set chart-specific exceptions in that site's `[dpf.services.<service>.extra_helm_values]` configuration, not in global chart defaults. The agent chart in [infra-controller PR #8798](https://github.com/dsx-ai-factory/infra-controller/pull/8798) accepts `hostNetwork`, `dpuClusterName`, `forgeSystem.apiServer`, and `serviceDaemonSet.hostAliases` for hosted-cluster discovery and API routing. The tested RHCOS DPU image lacks `/usr/sbin/lldpcli`, so this lab uses `lldpSidecar.enabled = false`; enabling the sidecar and mounting `/usr/lib64` alone leaves LLDP snapshots broken. Publish and pin the chart through the site's approved chart repository. The NCP deployment flow should not package a local chart into a lab ConfigMap or patch NICo-generated `DPUServiceConfiguration` objects.

Ensure both `carbide-api.forge` and `carbide-pxe.forge` resolve from DPU agent Pods to the corresponding reachable NICo endpoints. The agent init container fetches its bootstrap CA from `http://carbide-pxe.forge/api/v0/tls/root_ca` on every Pod start, including after NICo's UEFI restart. On a no-VIP lab using NCP's routes, set both names in the agent chart's site-specific `serviceDaemonSet.hostAliases` when site DNS cannot provide them, and verify the CA URL returns HTTP 200 from the DPU. The host alias is a lab-specific routing input; use DNS on a normal site.

NICo defaults to requiring two healthy ToR BGP uplinks. A provisioning-only lab without configured ToR peers can set the documented top-level site configuration `min_dpu_functioning_links = 0` to skip those health checks. This does not validate HBN peering or data-plane networking; require real BGP sessions and restore the intended policy before production acceptance.

`NICO_DPF_EXTERNAL=true` is for the upstream `infra-controller/helm-prereqs/setup.sh` installer path. NCP deploys NICo through its own Helm targets and does not invoke that script, so do not add that variable to NCP's `deploy.env` for this flow. If an installation uses the upstream setup script instead, follow its external-DPF instructions and the companion [infra-controller PR #8183](https://github.com/dsx-ai-factory/infra-controller/pull/8183).

## Manual prerequisites and validation

Before deployment, provide the DPF automation with the site-specific pull secrets, BFB endpoint, and DPU/host BMC inventory required by its Zero Trust profile. NICo also needs valid BMC credentials and inventory that lets secure discovery map the agent request to the correct machine interface. A BMC address is not a substitute for the source interface used by the discovery request. Set NICo's site-wide DPU BMC root credential to the actual password in `ZT_DPU_BMC_ROOT_PASSWORD` before NICo creates a `DPUDevice`: NICo publishes that credential into DPF's `bmc-shared-password` Secret. A mismatch can lock the BMC root account during DPF initialization. Use the NICo credential API or `nico-admin-cli credential add-bmc --kind=site-wide-root` with a protected password input, then verify the resulting Secret without printing it.

Before HCP generates DPU ignition, check that `DPFOperatorConfig.spec.provisioningController.registry.address` points to the current, DPU-reachable `bfb-registry` NodePort. The DPF #510 Zero Trust platform stage sets this address for a fresh deployment; an older cluster can retain a stale address or omit it. Also ensure the management API name in `DPFOperatorConfig.spec.overrides.kubernetesAPIServerVIP` matches the API serving certificate and resolves to the reachable management endpoint from the DPU out-of-band network. A correct `/etc/hosts` entry only on the management host does not fix DPU DNS. These are provisioning preflight checks, not post-install repair steps.

The NICo Core Helm upgrade runs database migrations. Configure `nico-api.envFrom.databaseCredentials.secretName` to an existing Secret containing the database `user` and `password` keys; in the lab the Crunchy Postgres operator supplied `nico-site-pg-pguser-nico`. Do not assume an ExternalSecret-generated migration credential exists. In HCP Zero Trust installations, hosted-cluster ignition can make the generated `bf.cfg` exceed DPF's 128 KiB guard. [HCP provisioner PR #353](https://github.com/rh-ecosystem-edge/dpf-hcp-provisioner-operator/pull/353) conditionally annotates the referenced DPUFlavor with DPF's supported size-check override; use a provisioner build containing that change when this condition occurs. The annotation applies to the whole flavor, so the PR rejects a flavor shared with another deployment.

The NICo/DPF handoff is not a complete end-to-end test by itself. Validate that the DPU agent registers, FMDS certificates are issued, the current DPU's service interfaces and service chain become ready, the DPU reaches `Ready=True` and `OperationalReady=True`, the worker is Ready in the HostedCluster, and NICo reports the managed host Ready. After reprovisioning, old `ServiceInterface` objects can retain a previous DPU node name; distinguish those from the current DPU's interfaces when assessing readiness. If NICo receives a proxy or egress address that has no matching machine interface, resolve that source-address mapping with the NICo networking/inventory owner; do not disable secure discovery or patch generated DPF resources as a workaround.
